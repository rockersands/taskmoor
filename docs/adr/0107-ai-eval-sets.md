# ADR-107: AI eval sets and their runner, on a seeded synthetic dataset

- Status: Accepted
- Date: 2026-11-01
- Backlog: M1-133

## Context

M1-079 builds the first AI features: summaries (AI-013), natural language to query (AI-014) and
duplicate suggestions (AI-016). Its exit criteria are numbers: at least 85% exact-result match
for natural language to query, a summary rubric that passes, duplicates found. Numbers need a
corpus that does not move, a scoring rule that cannot be argued with, and a runner that is proved
before any model is plugged into it. This environment has no AI provider key and none may be
added, so nothing here can call a model; the bundled embedding model (M1-078) has no runtime on
this branch yet.

Three properties matter most:
- **Permissions are part of the answer.** "My open bugs" means a different set for each person,
  and a summary must never use a comment its reader may not see (AI-013 (2)). A corpus of plain
  text pairs cannot test either.
- **Results, not strings, are compared for queries.** `stage != closed` and
  `status IN (New, Active, "In Review")` are the same query on this dataset; a string match would
  fail one of them.
- **Synthetic data only** (ADR-003), with provenance on every file.

## Decision

Everything lives in `apps/server/src/ai/evals/` (eval tooling: the server never imports it).

**The dataset** (`dataset.ts`, `seed.ts`): eight invented people, four groups, four tracks
(Web app, Platform API, Mobile apps, and Operations, which only three people browse), Members and
Viewers roles, releases (some shipped), areas, a Points field, and 203 tickets: 191 generated by a
seeded generator from word lists, plus the 12 summary cases. 261 comments, 16 of them restricted
to the security group. It is seeded through the app's own API in process (`buildApp`,
`app.inject`), each write by the person the dataset names, including the transitions to each
status. Only the past is set with SQL afterwards: creation, update, close and comment times, and
the times of each ticket's change history. The clock is fixed: now is 2026-09-16 10:00 UTC (a
Wednesday; weeks start on Sunday), and every query runs at that now in UTC. Seeding takes about
28 s.

**Natural language to query** (`query-corpus.ts`, `query-eval.ts`): 125 pairs (77 English, 16
each in Spanish, German and Japanese) of `{ id, prompt, language, asUser, reference }`, tagged
with what they cover: fields, operators, dates, functions, text search, ordering, empty values,
negation, "my", "this week", "overdue", "unassigned", history and permissions. References are in
the native query language. The expected result is not stored: it is what the reference finds as
that person, through the search API's own path (`prepareSearch`, the person's ticket filter,
compiled pages read in a read-only transaction). The keys are kept in a golden file for review.
A candidate's query scores when it finds exactly the same tickets; where the prompt asks for an
order, in the same order, with tickets the reference ranks equal (equal sort values) in any order
among themselves. A query that does not parse scores 0 and is never run; one that the resolver
refuses scores 0 too. One pair expects nothing on purpose and says why.

**Summaries** (`summary-corpus.ts`, `rubric.md`, `judge-prompt.md`, `summary-eval.ts`): 12
cases, each a ticket with a thread of four or five comments, a reader who sees the track but not
its restricted comments, the facts a summary must hold (status, assignee, blocker, next steps, as
phrases), the marker phrases planted in the restricted comments, one reference summary graded
pass and two or three flawed ones graded fail with the criteria they fail: 39 graded examples in
all. The automatic grader checks length, the four facts, that citations name comments of the
ticket, that nothing restricted is cited or repeated, and that every person, release number, date
and ticket key in the summary appears in what the reader sees. It agrees with all 39 examples
(verdict and exact set of automatic criteria). Purpose, contributors, recent changes and
faithfulness need judgement: they are written as a judge prompt that M1-079 runs with a model and
calibrates on the same examples first. A candidate summariser gets the ticket and a request
function that acts as the reader, so it can only read what the reader may; its citations are
comment ids, which the runner maps back to the thread.

**Duplicates** (`duplicates-corpus.ts`, `duplicates-eval.ts`): 22 clusters of two or three
tickets describing one problem in different words, one near miss per cluster that shares its
words but not its problem, and 8 unrelated tickets: a pool of 76 and 46 queries (each cluster
member once). The runner takes `embed(texts) => vectors` and an optional `rerank` (AI-016's model
step), ranks the pool by cosine similarity and reports recall@3 (the score), MRR, and the share of
queries where a near miss ranks above every true duplicate. Until M1-078's runtime is on the base
branch, a bag-of-words embedder stands in and the real score is reported as pending.

**The runner:** `pnpm eval <query|summary|duplicates|all> [--candidate <module>] [--json]
[--failures=N] [--database-url <admin url>]`. Query and summary seed a fresh database cloned from
the migrated test template and drop it afterwards. A candidate module exports
`{ name, query?, summary?, embed?, rerank? }` (`runner.ts`). With no candidate the runner proves
itself: the references (query must score 100%), the baselines, and the grader self-check; it exits
1 if one of those is off.

**Thresholds for M1-079** (`THRESHOLDS` in `runner.ts`): natural language to query at least 85%
exact-result match; every summary case passing the automatic criteria (and the judged ones once
a model runs them); duplicates recall@3 of at least 80% with the bundled model. The 80% is
proposed here, as "duplicates found" gives no number; the user may change it.

## Options considered

| Option | For | Against |
|---|---|---|
| Seeded dataset through the API, expected results computed by running the references (chosen) | Results follow permissions and the real query engine; nothing stored can drift from what the engine does | About 28 s to seed per run; a change to the engine's results shows as a golden diff to review |
| Hand-written expected ticket lists | No database needed | 125 lists to keep in step with every dataset change; errors in the lists, not in candidates |
| String match on the generated query | Trivial | Equivalent queries fail; a query that parses but finds the wrong tickets could pass after normalising |
| A model as the only summary grader | Judges everything | Needs a key; not reproducible; cannot be proved here. The automatic grader catches leaks and invented entities with certainty, the model judges the rest |
| Using `pnpm gen`'s benchmark dataset | Already exists, large | Written straight to tables, not through the API; no comment threads or restricted comments; no fixed clock for dates |

## Consequences

- M1-079 plugs its features in with `pnpm eval all --candidate <module>` and reads its scores
  against the thresholds; the same corpus measures prompt and model changes later.
- The dataset is the eval's contract: changing it changes the expected results. The golden file
  of expected keys shows every change for review.
- The summary grader's grounding check is deliberately narrow (people, release numbers, dates,
  ticket keys). Invented causes or decisions are the judge's to catch.
- The duplicate corpus is English only, as the bundled model is. Cross-language duplicates need
  a multilingual model and their own cases.
- Revisit when the bundled model's score is in: if recall@3 is well under 80%, either the corpus
  is too hard for embeddings alone or the threshold should assume the model re-ranking step.

## Provenance

Every corpus file is synthetic, written for Taskmoor on 2026-11-01 by the M1-133 task, in our own
words; no real person, company, ticket, query log or product text, and nothing copied from
another product (ADR-003). Names are invented, addresses use `example.com`, the restricted marker
phrases are invented capitals. Each file says so at its top, with how to add cases:
- a query pair: add it to `query-corpus.ts` with its tags, run the eval tests, review the golden
  file of expected keys;
- a summary case: add a ticket, thread, reader, facts, markers and graded summaries to
  `summary-corpus.ts`; the grader must agree with the new labels;
- a duplicate cluster: two or three tickets and a near miss in `duplicates-corpus.ts`.
