# ADR-068: Full-text search: stemmed word columns, the search syntax as tsquery, relevance, and counts estimated from block samples

- Status: Accepted
- Date: 2026-10-30
- Backlog: M1-040

## Context

QRY-007 asks for `~` on every text field and the master `text` field with the syntax of spec 01b
section 1.8 (words ANDed, phrases, a trailing `*`, single `?`, `term~` fuzzy, `-term`
exclusions, case-insensitive, stemming in the site's language, backslash escapes), served by an
index updated in the same transaction as the write: a ticket must be findable within a second
of being saved, and a ticket whose only match is a comment must be found by `text ~`. QRY-009
(3) asks for an approximate total in under 100 ms. M1-040's done-when: the conformance Text
section green, p95 under 300 ms at 10M tickets, counts within 10%.

M1-037 shipped a subset: every word must occur, as written (`simple`), through GIN indexes on
expressions (migration 0043); the first page counted to 10,000 and said "more than" beyond
(ADR-010). ADR-011 chose Postgres full-text search with `pg_trgm` for short text, ranking with
weights, and one configuration per instance.

## Decision

### Words and indexes (migration 0057)

- **`taskmoor_search`**, a text search configuration: a copy of `english` whose word mappings
  use a Snowball English dictionary without a stop-word list. Words match their other forms
  ("logging" finds "logs"); "the", "not" and "it" stay searchable, so no search is silently
  empty and a phrase keeps all its words. English is the only language the product ships; a
  site language later means altering this configuration's mappings and rewriting the word
  columns (an operator command, not built), with no change to queries.
- **Stored word columns**, generated by Postgres from their source on every write, so a ticket
  is findable as soon as its transaction commits (QRY-007 (3)): `ticket.summary_words`,
  `description_words`, `environment_words`, `ticket_comment.body_words`. Rich-text documents
  are read by `taskmoor_document_text(jsonb)`, an immutable SQL function that joins the text
  nodes of each block as written (marks split a word into several nodes) and keeps blocks and
  hard breaks apart; the first 200,000 characters are indexed (a `tsvector` holds at most 1 MB).
  Stored, not expression indexes, because rechecks and ranking read the vector per row, and an
  expression would extract and parse the document again each time. Each column has a GIN index
  over rows outside the trash. Custom text values (`v_text`, short: a paragraph's first 255
  characters) keep an expression GIN index.
- **`pg_trgm`** with trigram GIN indexes on summaries and custom text values, for patterns. The
  extension is trusted (PostgreSQL 13 and later): the database's owner creates it; the compose
  README says so for external servers.
- The schema snapshot now records each generated column's expression, so the golden file shows
  what the word columns hold.

### The syntax (spec 01b section 1.8)

`parseTextSearch` (`packages/query/src/text.ts`) reads a `~` value into terms; the resolver
refuses what cannot run (a search that only excludes, one with no letter or digit, a fuzzy
wildcard, more than two `?` in a word, a pattern without three letters or digits together) at
the value's position, so the query editor shows it. The server (`search/text.ts`) turns terms
into the input of `to_tsquery` over `taskmoor_search`, one parameter per search, operands
quoted and escaped, so the database's own parser splits and stems them exactly as it did the
indexed text:

| Typed | Means | SQL |
|---|---|---|
| `login timeout` | both words, any order | `'login' & 'timeout'` |
| `"login failed"` | the words next to each other, in order | `'login failed'` (the parser makes it `'login' <-> 'fail'`) |
| `log*` | words that start so | `'log':*` |
| `lo?in` | one character for `?` (at most two) | an OR of the words it stands for |
| `login~` | the word or one edit away (Damerau: a character removed, added, changed, two neighbours swapped) | an OR of the words it stands for |
| `-password` | must not occur | `!'password'` |
| `*Exception`, `Null*Exc?ption` | a pattern: `*` anywhere but the end, `*` any characters and `?` one | `ILIKE '%Exception%'` on summaries and text fields |
| `C\+\+` | the backslash makes the next character literal | `'C++'` |

- **Expansions instead of rechecks.** `?` and fuzzy words become the words they stand for
  (letters, digits, the word's own characters and Latin-1 accented letters; a fuzzy word of 3 to
  24 characters), each an exact lexeme the word index looks up, each stemmed like the indexed
  words were. The binder then keeps only the words that occur in some searched text of the
  workspace (`pruneExpansions`: one index lookup per word in one statement), because the planner
  cannot weigh an OR of seventy words and would walk the whole order for a rare one. A search
  whose words do not occur keeps one word that matches nothing.
- **Patterns** need the trigram indexes, which only short texts have: summaries and text fields
  take them; description, environment, comment and history (`WAS`, `CHANGED`) refuse them with
  a message; `text ~` applies them to summaries and text fields and says so in a warning.
- Phrases do not cross a block boundary as one word would (blocks are joined with a space), but
  a phrase may span the end of one paragraph and the start of the next.

### The master text field

`text ~` matches a ticket whose summary, description or environment, a comment the viewer
reads, or a text field matches. Two forms, chosen when the query is bound from the planner's
estimate of the matches (one `EXPLAIN` of the set form, a millisecond or two):

- **Few matches** (fewer than 5,000 and 0.3% of the tickets): one set of ids that does not
  depend on the row, `k.id IN (tickets UNION ALL comments UNION ALL text fields)`; the planner
  starts from the word indexes and sorts the few matches. An OR of the five places can only
  walk the order, which reads the whole table for a rare word. The comment branch reads each
  matching comment's track by primary key, so it stays one table (a join made the planner hash
  the whole ticket table).
- **Many matches:** an OR of the five places as a test of the row, so walking the order stops
  after a page. The set form would read every match first: Postgres estimates the distinct ids
  of a UNION ALL at 200 whatever they are, so it always starts from the set.

### Relevance

`ORDER BY relevance` (a system field only ORDER BY takes; the resolver refuses it without a text
search that must match, and in a condition) orders by the weighted sum of `ts_rank` with length
normalisation over the searches that must match: summary 1, description 0.4, environment 0.2,
custom text 0.4, the best comment the viewer reads 0.2; `text ~` ranks by summary, description
and environment (comments and text fields make it match but do not raise its rank, which keeps
ranking every match cheap). Relevance is a place in a ranking, as rank is on a board:
ascending, the default, puts the best match first. The value is negated `float8`, so keyset
cursors carry it exactly and ties fall back to the ticket id.

### Counts

`total: { count, exact, approximate? }` (`search/count.ts`):

- **Exact up to 10,000**, as before: the count reads matches until one past the cap.
- **Beyond, an estimate**: the query judges every row of a sample of the ticket table's blocks
  (`TABLESAMPLE SYSTEM` with a seed fixed per query, so a count holds still while nothing
  changes): matches per sampled block, times the blocks the table has now (`pg_relation_size`,
  exact; the planner's row count can be behind and only sizes the sample). Blocks are sampled
  whole and matches cluster in them, so the error is judged from the sample: the standard error
  of a cluster sample's mean with the finite population correction. An estimate is given only
  when that error is at most 3.5% of it, so the count is within 10% 99 times in 100 or more
  (`approximate: true`); otherwise the sample grows once, sized by the error it saw, to at most
  500,000 rows, and if that is still not enough the total stays "more than 10,000" (both flags
  false). The first sample reads about 20,000 rows. A Horvitz–Thompson estimate (matches over
  the share sampled) was tried first; its error counts the luck of how many blocks were drawn,
  so even evenly spread matches looked uncertain.
- **Cached** for `TASKMOOR_COUNT_CACHE_SECONDS` (default 60; 0 keeps none), in each process, per
  statement and parameters (they hold the viewer's filter, so an entry never serves another
  filter), at most 1,000 entries; an entry is dropped when more tickets of the workspace changed
  since than 2% of its count. Only estimates are kept: exact counts are cheap and stay exact.
- The web says "About 123,456 tickets" for an estimate and "More than 10,000 tickets" for a lower
  bound; subscription emails say "about".

## Options considered

| Option | For | Against |
|---|---|---|
| Stored word columns per text (chosen) | Exact per-field search, cheap rechecks and ranking, phrases stay inside a field | A column and an index per text; changing the language rewrites them |
| One weighted vector per ticket (`A` summary, `B` description, `C` environment) | One index | Per-field search through weights is lossy in GIN (every row with the word anywhere is rechecked); phrases join the end of one field to the start of the next |
| Expression indexes (0043) | No stored column | Every recheck and rank extracts and parses the document again |
| Trigram index on every text for `?` and fuzzy | No expansion | Large indexes on long text; stems and trigrams disagree |
| A vocabulary table for fuzzy words | Any edit distance | A write on every save to keep it, contention on new words |
| Planner estimate or `count(*)` with a timeout for totals | Simple | Estimates are off by orders of magnitude under the permission filter; a timeout gives no number |
| Bernoulli row sampling for totals | No clustering | Reads every block of the table |

## Consequences

- Every writer of summaries, documents and comments gets its words indexed for free; nothing in
  the application maintains them. Any reader that selects whole ticket rows now also reads the
  word columns.
- Fuzzy matching is one edit, and `?`, prefixes and fuzzy words match the indexed (stemmed)
  words: `runn*` does not find "running", whose stem is "run" (as in Lucene-based search).
- `text ~` relevance ignores comments; ordering a very common word by relevance ranks all its
  matches, which is the cost to watch at 10M.
- Clustered results (the newest 15%, one track's last months) seldom get an estimate: their
  matches sit in few blocks, so they report "more than 10,000".
- Revisit when a second site language ships, when the 10M runs (M1-117) show the common-word
  forms or relevance over budget, or for an OpenSearch adapter (ADR-011, M2).
