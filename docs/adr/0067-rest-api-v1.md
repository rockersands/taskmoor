# ADR-067: REST API v1 as a written contract of stable operations over the server's own schemas

- Status: Accepted
- Date: 2026-10-30
- Backlog: M1-065

## Context

API-001 asks for a versioned native REST API covering all functionality. Its checks:

1. Every UI action used in end-to-end tests has a matching public endpoint.
2. The OpenAPI document validates and generated clients compile.
3. A repeated POST with an Idempotency-Key creates one ticket.

M1-065 asks for OpenAPI 3.1 written contract first, cursor paging, original reference docs and
a generated TypeScript SDK. It is done when contract tests from OpenAPI are green, a
breaking-change diff check runs in CI, and the docs have no broken links.

The server already answers about 440 routes under `/api/v1`. They validate input with zod 4
(which exports JSON Schema 2020-12, OpenAPI 3.1's dialect), and they record their routes in
`app.routeTable`. Token scopes already classify each route (ADR-035).

## Decision

- **Two kinds of route.**
  - **Stable operations** are the API's promise for all of v1: sessions, tracks, tickets,
    transitions, rank, history, comments, links, time entries, search, saved searches, boards,
    sprints, releases, and reference data. There are 48 of them, each with an id such as
    `getTicket`.
  - **Internal routes** are every other route. They serve the web app's screens and may change
    in any release. They are still listed in the document, so nothing the server answers is
    hidden.
  - More stable operations are added as programs need them.
- **The contract is written first, in code** (`apps/server/src/api/operations.ts`). Each stable
  operation has:
  - its method and path, its id, its area, and what it does in our own words;
  - its request, which is the zod schema its route validates with (exported from the route,
    so the document cannot drift from validation);
  - its success responses, as zod schemas in `api/schemas.ts`. Objects are loose, so a field
    added later is compatible.
  - Error responses share one shape (`{ error, fields? }`) and are added to every operation.
  - Security and access come from the token scope map.
- **The document** (`docs/api/openapi.json`) is built by `api/openapi.ts` from the catalogue
  and the route table, with named schemas as components. It is committed, and
  `pnpm verify --update` rewrites it, so changes are reviewed in the diff. A test checks it
  against the OpenAPI Initiative's 3.1 schema (`@apidevtools/openapi-schemas`, with ajv). That
  schema's `$dynamicRef #meta` points to its own schema definition, because ajv supports
  dynamic references only in part.
- **Contract tests from the document** (`api/contract.test.ts`):
  - Every stable operation is called against a real server.
  - Its status must be documented, and its body must validate against the documented schema.
  - A stable operation the test never calls fails the test.
  - The ticket list is read page by page to its end, each ticket once.
- **Paging**: stable lists take `limit` and `cursor` and answer `next` (null on the last
  page). The ticket list also accepts `cursor` now; its old name `after` still works. Comments
  and time entries page by id, so their `next` is a number, and the document says so.
- **Breaking changes** (`api/diff.ts`):
  - Each change is compared with `docs/api/baseline/openapi-v1.json`, the contract as v1
    publishes it.
  - Breaking: a stable operation gone, a parameter gone or newly required, a closed body's
    property gone or newly required, an enum losing a value, a success status gone, a
    response property gone or changing type.
  - Additions are never breaking.
  - The check is a test, so `pnpm verify --ci` runs it in CI and fails the build. A breaking
    change means a v2, not an edited baseline.
- **SDK** (`packages/sdk`, `@taskmoor/sdk`):
  - Types for the stable operations are generated by openapi-typescript (MIT, a development
    dependency), together with a table of methods and paths.
  - A small fetch client, `createClient({ baseUrl, token }).call(id, { path, query, body })`,
    is typed from them. `pages` reads paged lists, and refusals throw `TaskmoorError`.
  - The generated files are committed. A test fails when they lag the document, and a server
    test drives the SDK against a listening server with an API token.
- **Docs**: `docs/api/README.md` is written by hand and covers stability, authentication,
  requests, paging, errors, rich text, the SDK and how to change the API.
  `docs/api/reference.md` is generated from the document. A test checks that every link and
  anchor in both resolves.

## Options considered

| Option | For | Against |
|---|---|---|
| Catalogue in code over the routes' own schemas (chosen) | Requests cannot drift from validation; responses held to real answers | Response schemas are written by hand |
| A hand-written YAML document | Readable, tool-neutral | Nothing ties it to the code; it drifts |
| Fastify route schemas for every route | Validation and docs in one place | A rewrite of 440 routes; their checks are richer than JSON Schema |
| Documenting every route as stable | One kind of route | Freezes the web app's screens; v1 could never move |

## Consequences

- API-001 (1), every UI action used in end-to-end tests having a public endpoint, is met for
  the core flows; screens that use internal routes (administration, reports, dashboards) get
  stable operations as programs need them.
- API-001 (3), Idempotency-Key, is not built here.
- Rate limits and their dashboard are M1-066, the Jira-compatible contract M1-068, and the MCP
  server M1-072; all build on this catalogue.
