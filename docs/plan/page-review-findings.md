### Questions of direction, for the user

- Should the phone list stay a table, or become stacked rows like the phone backlog? This decides the fix for the worst fault in the group.
- Should the report links on a phone collapse behind a menu or a single picker, so a report shows on the first screen? On desktop they also take about 260 px.
- Should keyboard instructions be hidden on touch screens, or moved behind the help button at every width? The Tracks page already has a touch wording to follow.
- On pages with a tab bar, are the pills 'Track summary', 'Back to the board', 'Backlog' and 'Reports' wanted? They repeat a tab and take a row on phones. Outcomes and Files have none.
- Should the outcome burndown and outcome report keep a typed ticket key? The release reports offer a picker, and the track's outcomes are already known to the Outcomes page.
- Page title pattern: 'Calendar of Mobile apps', 'Outcomes', 'Backlog and sprints', and a board titled just 'Mobile apps' with a line above. Should these be one pattern? Should the board settings title say 'board'?
- Board column minimum width: keep 16 rem, as ADR-114 says, and scroll sideways at 1280, or let four columns fit? Whichever you choose, the hard cut needs a cue.
- 'Ship this release...' is a full-width filled bar at 1280, alone in its own card, unlike every other action in the group. Is that intended for a weighty action?
- Filter panels such as Board filters stand on the canvas as faint wells, and they are barely visible in light. ADR-114 describes a form fieldset on the canvas as a slab. Should these be slabs, or are they deliberately quiet?
- The hatched bar on the timeline (MOB-2) has no explanation on the page. Should it have a legend?
- Should the phone calendar drop empty days and add weekday names, or stay a full month?

### Questions of direction

- Should the phone ticket table (track list, search results, plan list) become stacked rows instead of a table? All three seem to share one component, so one decision covers the three high findings.
- Should the Home welcome tutorial collapse, or move below the person's own work, once it has been seen? On a phone it takes 3.7 screens.
- Should menus, the command palette and dialogs be opaque, or at least veil the page fully? The glass look currently lets text show through.
- Should the create form leave out fields that can only be set after creation, or allow them at creation? Is 'Close reason' wanted there at all?
- Should the wallboard have its own large-type, full-screen layout without interactive controls?
- Should the section be named 'Plans' instead of 'Multi-track'?
- Should not-found pages share one pattern, with a title, a way back to the list and no section highlighted?
- Should a bulk change with failures end in a warning rather than a green 'Done.', and name the change made?
- On desktop, should the capacity table show fewer periods per view, or scroll sideways with a visible cue?
- On a phone, should the ticket's Details come before Activity, and should plan filters collapse behind one 'Filters' button?

### Questions of direction

- Admin side list at desktop width: should it be sticky, collapse its groups, or link the group pages from their headings, so short admin pages are not 1700 px long?
- Admin page list on a phone: should it be one pattern, either a bar at the top or a card at the bottom, on the overview as well as the sub-pages? If it stays a bar, should it carry a chevron?
- Audit log and API usage on a phone: stacked rows (time, who, action as one block) or a table that scrolls sideways with a cue? Should action codes such as 'ticket_template.created' be shown as plain words?
- Create forms: some pages put a full create form above the list (Groups, Teams, Tracks, Fields, Roles); others use a 'New ...' button (Ticket templates, Webhooks, Directories, Identity providers). Which pattern should admin pages follow?
- Guardrails has eleven 'Save the limit' buttons. Should the page have one save, as Rate limits on API usage does?
- Which word names the whole installation in the interface: workspace, instance or site?
- Should session lengths be entered in days (or with a unit picker) rather than hours and minutes?
- Should destructive actions (Deactivate, Erase, Delete, Revoke tokens) get a distinct style or always confirm?
- Should the workflow diagram's boxes be reachable by keyboard and named, or hidden from assistive technology on purpose because the lists below repeat them?

### Questions of direction

- Should a signed-out visitor see the whole signed-in navigation (Inbox, Dashboards, Multi-track, Settings, the search field), or a reduced frame? Today Home shows a sign-in card, Tracks a false empty state and Inbox a sign-in form.
- Should the stand-alone pages (setup, password, invite, unsubscribe, app consent) carry the product name and one fixed way out, such as always 'Go to sign in'? Should their intro lines be hidden when an error shows?
- Should the sign-in page offer a path for a forgotten password, whether self-service or 'ask your administrator'? There is none, including after a wrong password.
- For an address that matches no page: a not-found page with links to Home and Search, or Home with a notice? The same question applies to track and board not-found: show the track's tabs, or a plain page with a way back?
- Should Account be split into sections or tabs (Profile, Notifications, Security, Tokens, Your data), or get an index, given its 4000 to 5500 px length? Should /account/notifications show only notifications rather than scroll the whole page?
- Should the notification table become stacked rows per event on phones? Spanish breaks it at 375 now.
- Should a signed-out visitor following an app-consent link learn that the request is unknown before signing in, or only after (the current behaviour)?
- The Spanish catalogue keeps 'track' and 'ticket' ('grupo de tracks', 'Ticket creado'). Is that the intended product vocabulary in Spanish?
