# 05b Administration, security and self-hosting: deployment, operations and non-functional requirements

This file specifies how Taskmoor is installed, connected, upgraded, backed up and observed, and the non-functional targets every module must meet. Taskmoor ships as two pieces: a backend the customer hosts (API, workers, realtime service and PostgreSQL) and a static frontend that runs on any domain or static host. The Taskmoor Builder produces both from one form, so connection settings match on both sides without manual wiring. Easy self-hosting is a product requirement with measurable targets, not documentation: a fresh VM must reach a working app on a domain in under 15 minutes, and a team of up to about 500 users must run on 2 to 4 vCPU and 4 to 8 GB of RAM.

## How to read

- **ID**: `MODULE-NNN`, stable and never reused. This file holds OPS and NFR.
- **MS**: M1 = release 1.0, Jira Software parity and Data Center exit core; M2 = enterprise, automation and service-desk core; M3 = ITSM, operations and CMDB; M4 = discovery, portfolio, quality and ecosystem.
- **Pri**: M = Must, S = Should, C = Could.
- **Source**: parity target. "exceeds Jira" marks a deliberate improvement; "verify" marks a fact the research flagged as unconfirmed. Sizing and performance figures are Taskmoor targets to be proven by the load-test kit, not measurements.
- **Terms**: backend kit and frontend kit = the two Builder outputs; instance = one backend installation with its own id and key pair.

## 1. Reference: deployment model

### 1.1 Pieces

- **Backend** (customer-hosted): one multi-architecture container image (amd64, arm64) running the API, background workers and realtime service, with the role chosen by environment variable; PostgreSQL is the only required stateful service; S3-compatible storage and an external search engine are optional. The image also contains the matching frontend build used by the Builder and the optional same-origin mode.
- **Frontend kit**: static files only, no server code, for any static host (shared hosting with cPanel, S3 plus CDN, Netlify, Cloudflare Pages, nginx).
- **Taskmoor Builder**: a static web page that runs entirely in the browser (secrets generated with WebCrypto, zips built client-side, nothing transmitted) and a CLI, both built on one core library (`@taskmoor/builder-core`).
- **Connection manifest**: a document signed with the instance private key, listing instance id, instance public key, API URL, WebSocket URL, allowed frontend origins, backend version and kit version. Both kits contain it; the frontend checks it against the backend's meta endpoint (API-017) before running.

### 1.2 Builder inputs

| Input | Required | Goes into |
|---|---|---|
| Backend public URL; frontend URL | Yes | Both kits (frontend URL becomes the allowed origin and OAuth redirect base) |
| Instance name; default language | No (defaults) | Both kits |
| Branding: logo, favicon, colours | No | Frontend kit (and backend for emails) |
| Routing mode: clean URLs (default) or hash routing | No | Frontend kit |
| SMTP host, port, user, password | No | Backend kit only |
| AI provider and key | No | Backend kit only (moved to encrypted storage on first boot, IAM-020) |
| Deployment target: Docker Compose on a VPS (default), Helm values, single binary (M2) | No | Backend kit |
| Generated by the Builder: database password, token-signing keys, encryption master key, instance key pair, one-time setup token, instance id | Automatic | Backend kit; only the instance id and public-key fingerprint go to the frontend kit |

### 1.3 Kit contents

- **Backend kit (zip)**: `docker-compose.yml` pinned to the exact backend image version; PostgreSQL service with a named volume; Caddy reverse proxy with automatic HTTPS for the API domain; `.env` with generated secrets, `PUBLIC_URL`, `ALLOWED_ORIGINS` (the frontend URL), OAuth redirect URIs and `INSTANCE_ID`; `install.sh` and `install.ps1`; the connection manifest; a README listing the DNS records to create; Helm `values.yaml` when that target is chosen.
- **Frontend kit (zip, or one self-contained `index.html`)**: `index.html` with public configuration baked in and integrity hashes for every asset; hashed asset files; the connection manifest; routing fallbacks `.htaccess`, `_redirects` and an nginx snippet; `version.json`.

### 1.4 Sizing targets

| Active users | Topology | vCPU | RAM | Notes |
|---|---|---|---|---|
| Up to 50 | All-in-one with bundled PostgreSQL | 2 | 4 GB | Small team default |
| Up to 500 | All-in-one, or app plus PostgreSQL | 2 to 4 | 4 to 8 GB | Headline target |
| Up to 2,000 | App node plus external PostgreSQL | 8 in total | 16 GB in total | |
| Up to 10,000 | HA: 2 to 3 app nodes, worker pool, PostgreSQL primary and replica, S3 storage | about 24 | about 64 GB | Helm chart |
| Up to 100,000 | HA scaled out, optional external search | 64 or more | 256 GB or more | Proven by benchmark before claiming |

For comparison, OpenProject asks 4 cores and 4 GB for up to 200 users, 8 and 8 GB for 500, and 16 and 16 GB for 1,500.

## 2. OPS requirements

| ID | Requirement | Acceptance criteria | MS | Pri | Source |
|---|---|---|---|---|---|
| OPS-001 | **One-command install.** Taskmoor shall install from the backend kit with one command (`install.sh` or `install.ps1`), which checks prerequisites, starts the stack, waits for health and prints the first-run setup link. | (1) On a fresh Ubuntu LTS VM with Docker missing, the script explains how to install it and exits cleanly. (2) With prerequisites present, the setup link prints within 5 minutes. (3) In same-origin mode a fresh VM reaches a working sign-in in under 10 minutes, timed in CI. | M1 | M | User requirement; Plane; GitLab Omnibus |
| OPS-002 | **Dependencies, footprint and sizing.** Taskmoor shall need only PostgreSQL as stateful service (bundled container for small teams, external server for production), keep S3 storage and external search optional, publish the sizing table of section 1.4 and ship a load-test kit that reproduces it. | (1) The full feature set runs with PostgreSQL and local disk only. (2) A 500-user load profile runs within 4 vCPU and 8 GB. (3) The load-test kit reports pass or fail against each sizing row. | M1 | M | OpenProject sizing; exceeds Sentry and Huly footprints |
| OPS-003 | **First-run setup.** Taskmoor shall run a setup wizard reached by the installer's link and protected by the one-time setup token: create the first admin, confirm public URL and allowed origins, test SMTP, confirm AI settings, optionally create a sample space; the same steps run headless from configuration. | (1) The setup token works once and expires after use or 24 hours. (2) Headless setup with a config file yields the same state as the wizard. | M1 | M | User requirement |
| OPS-004 | **Configuration and secrets.** Taskmoor shall read configuration from one environment file with overrides by variable, provide a validate command, and read secrets from files, environment, HashiCorp Vault or cloud secret managers. | (1) The validate command reports every invalid or missing setting with its name. (2) Secrets never appear in logs or the status page. | M1 | M | Jira DC (Vault secrets) |
| OPS-005 | **Air-gapped installation.** Taskmoor shall install without internet from an offline bundle (backend image archive, frontend builds, Builder page, checksums, SBOM in SPDX or CycloneDX, signatures), use a private registry, make no outbound calls by default (telemetry and update checks off), and work with local AI models only. | (1) A full install and Builder run succeed on a network with no route to the internet. | OPS-006 | **Safe upgrades.** Taskmoor shall upgrade with one command that runs pre-checks (upgrade path, disk space, extension compatibility, recent backup), takes an automatic backup, applies forward-only idempotent migrations (online for large tables), rolls back automatically on failure, offers a dry run, and needs no manual per-version steps; the Builder regenerates the frontend kit for the new version from the saved project file. | (1) A failure injected mid-migration restores the previous version and data automatically. (2) Upgrading a 10M-item database keeps the site readable during migration. (3) A dry run lists every migration with time estimates. | M1 | M | Jira DC; exceeds Huly (manual steps) |
| OPS-007 | **Release channels and long-term support.** Taskmoor shall publish stable, long-term-support (security fixes for at least 24 months) and preview channels with signed releases and release notes. | (1) Each release is signed and its SBOM published. (2) LTS releases receive security fixes for 24 months. | M1 | M | User requirement; report recommendation |
| OPS-008 | **Scheduled backups.** Taskmoor shall back up database, attachments and configuration on a schedule to local disk, S3 or SFTP, encrypted, with retention rules, automatic verification by test restore, and optional point-in-time recovery from database log archiving. | (1) A nightly backup with 14-day retention keeps exactly 14 backups. (2) The weekly verification restores into a scratch database and reports success. | M1 | M | Atlassian Backup and Restore (paid add-on); exceeds Jira |
| OPS-009 | **Restore, including user-error recovery.** Taskmoor shall restore a backup with one command to the same or a new host, restore a single space or deleted items into the live site, and restore into a sandbox. | (1) A full restore to a new VM reproduces the site. (2) A space deleted yesterday is restored from last night's backup without touching other spaces. | M1 | M | exceeds Jira (Atlassian backups do not undo customer deletions) |
| OPS-010 | **Health, status and jobs.** Taskmoor shall expose liveness and readiness endpoints, an admin status page (database, queues and lag, search index lag, storage, email, disk, background jobs, versions of backend and connected frontends), online reindexing, a job console with retry and cancel, and a support bundle with redacted logs. | (1) Stopping PostgreSQL turns readiness red within 10 s. (2) A full reindex runs while users keep working. (3) The support bundle contains no secrets. | M1 | M | Jira DC |
| OPS-011 | **Observability.** Taskmoor shall publish Prometheus metrics, OpenTelemetry traces and logs, structured JSON logs, and example dashboards and alert rules. | (1) Request latency, error rate, queue depth and database pool metrics are scraped by Prometheus. (2) A trace follows one request from API to database and worker. | M1 | M | Report recommendation |
| OPS-012 | **Email infrastructure.** Taskmoor shall send mail through SMTP with TLS or OAuth (Microsoft 365, Gmail), retry with a queue, handle bounces, and receive mail for item creation and comments through mail handlers. | (1) An SMTP outage of 30 minutes delays but loses no notifications. (2) A mail handler creates items from a mailbox (Atlassian's migration tool drops mail handlers). | M1 | M | Jira DC |
| OPS-013 | **Static frontend kit.** Taskmoor shall produce the frontend as static files with no server code, as a zip (default) or one self-contained `index.html`, routing without host configuration through hash routing or the generated `.htaccess`, `_redirects` and nginx fallbacks for clean URLs. | (1) The zip uploaded to Apache shared hosting, an S3 bucket with CDN, Netlify, Cloudflare Pages and nginx serves deep links such as `/browse/ABC-1` (clean URLs) on each. (2) The single-file build works when opened from a static host with no other files. | M1 | M | User requirement (Builder) |
| OPS-014 | **Taskmoor Builder.** The Builder shall take the inputs of section 1.2 in one form, validate them, generate all secrets, and emit both kits of section 1.3 with the same signed connection manifest, so URLs, origins, redirect URIs and instance identity match on both sides. | (1) For every combination of deployment target and routing mode, kits from one form pass a consistency check (origins, URLs, instance id, fingerprint). (2) Invalid URLs (for example http on a public domain) are rejected with a message. | M1 | M | User requirement (Builder) |
| OPS-015 | **Backend kit.** The Builder shall produce the backend kit of section 1.3, whose installer checks prerequisites (Docker, ports 80 and 443, DNS resolution of the API domain), starts PostgreSQL, the backend and Caddy with automatic HTTPS, waits for health and prints the setup link. | (1) On a fresh VM with DNS in place, `install.sh` produces a valid certificate and a healthy API. (2) The README lists exactly the DNS records needed for the chosen URLs. (3) The pinned image version equals the version recorded in the manifest. | M1 | M | User requirement (Builder) |
| OPS-016 | **Builder delivery and project file.** The Builder shall run as a static page entirely in the browser, offline-capable, and as a CLI on the same core library, and save a project file (secrets excluded, or included only when encrypted with a passphrase) for regenerating kits on upgrade or rebrand. | (1) A browser network capture during a Builder run shows no outbound requests. (2) CLI and web Builder produce byte-identical kits from the same project file and seed. (3) A rebrand from the project file changes only branding files in the frontend kit. | M1 | M | User requirement (Builder) |
| OPS-017 | **Frontend origins, versions and same-origin mode.** The Taskmoor backend shall let admins add or remove allowed frontend origins (updating CORS, WebSocket and OAuth redirect lists), list connected frontends with the kit versions they report, show an "update available" banner in frontends older than the backend, and optionally serve the frontend itself on its own origin. | (1) Adding a second origin lets a second frontend kit sign in without restart. (2) A kit one version behind shows the update banner. (3) Same-origin mode serves the bundled frontend with no Builder run. | M1 | M | User requirement (Builder) |
| OPS-018 | **High availability.** Taskmoor shall provide a Helm chart with several stateless API and realtime replicas, separate worker pools, nodes dedicated to API traffic or background work, external HA PostgreSQL and S3 storage, rolling upgrades with zero downtime, disruption budgets and autoscaling. | (1) Killing any one app pod during a load test causes no failed user requests beyond retries. (2) A rolling upgrade completes with zero downtime. | M2 | M | Jira DC clustering |
| OPS-019 | **Sandbox and configuration as code.** Taskmoor shall create a sandbox copy of production (full or configuration-only, with data masking), refresh or reset it, export all configuration as versioned YAML, diff two instances, and promote changes with a dry run. | (1) A workflow changed in the sandbox is promoted to production after reviewing the diff. (2) Masking replaces personal data in the sandbox copy. | M2 | M | Jira Premium (sandbox); CMJ app |
| OPS-020 | **AI spend limits and cost tracking.** Taskmoor shall track AI cost per user, feature and workspace from token usage and the editable price table (file 02c), alert at admin-set thresholds (default 80% and 100%), enforce hard stops per user and per workspace per day, week or month, and show a usage dashboard; Taskmoor itself meters nothing. | (1) A user over the daily limit gets "AI limit reached" and no provider call is made. (2) Alerts reach admins at each threshold. (3) Dashboard totals match the AI audit log. | M1 | M | User requirement; Linear spend limits; exceeds Jira (credit metering) |
| OPS-021 | **Admin insights and change control.** Taskmoor shall show usage analytics (daily, weekly and monthly active users, activity per space, storage per space, automation and API usage) and let admins delay new user-facing features per site through feature flags. | (1) Admins see active users per space for the last 90 days. (2) A new UI feature stays off until the admin enables it. | M2 | M | Jira Premium (admin insights, release tracks) |
| OPS-022 | **Multiple workspaces.** Taskmoor shall host several isolated workspaces in one installation, each with its own configuration, users and data, administered centrally. | (1) A user of workspace A cannot see any data of workspace B. | M2 | S | Jira Enterprise (up to 150 sites) |
| OPS-023 | **Single-binary backend.** Taskmoor shall offer a backend build that runs without Docker as one binary per platform plus an external PostgreSQL, selectable as a Builder deployment target. | (1) On a VM without Docker, the binary starts and passes the end-to-end suite. | M2 | S | User requirement (Builder) |
| OPS-024 | **Compliance builds.** Taskmoor shall provide a FIPS 140-3 mode using validated cryptography, a hardening guide, system-security-plan templates and control mappings for SOC 2 and ISO 27001, and reproducible builds. | (1) In FIPS mode, non-approved algorithms are refused. (2) Two builds of the same tag are byte-identical. | M4 | M | Report recommendation (regulated buyers) |

## 3. Reference: performance and scale targets

| Metric | Target |
|---|---|
| Open an item, warm cache | under 100 ms p95, server response plus render |
| Open an item, cold | under 300 ms p95 |
| Board with 5,000 cards | under 1 s to interactive |
| Query at 10M items (space, status, assignee, ordering) | under 300 ms p95 |
| Text search at 10M items | under 500 ms p95 |
| Create item round trip | under 200 ms p95 |
| Real-time propagation to other clients | under 1 s p95 |
| Permission check | under 10 ms p95 |
| Dashboard with 10 gadgets | under 2 s |
| Simple API read | under 100 ms p95 |

Scale: 30M items per site; 2,000 custom fields per site (700 per space by default); 30,000 spaces; 100,000 users; 25,000 groups; per item 1,000 comments, 1,000 links, 3,000 attachments and 50,000 history entries; 60,000 sprints; 120,000 epics. These cover Jira Cloud's guardrails (30M items, 30,000 spaces) and Jira DC's (1,200 custom fields, 7,000 projects).

## 4. NFR requirements

| ID | Requirement | Acceptance criteria | MS | Pri | Source |
|---|---|---|---|---|---|
| NFR-001 | **Performance budgets.** Taskmoor shall meet the latency targets of section 3 on the 500-user reference hardware with the 10M-item dataset. | (1) CI fails a release when any p95 target is missed in the benchmark suite. (2) Results are published per release. | M1 | M | exceeds Jira (slowness is the top complaint) |
| NFR-002 | **Scale targets.** Taskmoor shall operate at the scale of section 3 on the HA reference cluster. | (1) Benchmarks at 10M and 30M items, 30,000 spaces and 100,000 users pass the section 3 targets with at most 2x latency at 30M. | M1 | M | Jira Cloud and DC guardrails |
| NFR-003 | **Concurrency.** Taskmoor shall serve 500 concurrent active users with 25% writes on the HA reference cluster at under 500 ms p95 for interactive requests. | (1) The load-test kit scenario passes. | M1 | M | Jira DC OpenSearch benchmark (500 ms at about 210 users) |
| NFR-004 | **Durability and recovery.** Taskmoor shall lose no committed data on a node failure, achieve a recovery point of 15 minutes or less with log archiving and a recovery time of 1 hour or less from backup. | (1) A timed disaster-recovery drill on the reference dataset meets both targets. | M1 | M | Report recommendation |
| NFR-005 | **Accessibility.** Taskmoor shall meet WCAG 2.1 AA (and EN 301 549) in all interfaces, including portals, status pages and the Builder, with full keyboard operation, screen-reader support and published conformance reports. | (1) Automated accessibility checks pass on every page in CI. (2) A manual audit before each major release finds no AA failures. | M1 | M | Public-sector procurement |
| NFR-006 | **Internationalisation.** Taskmoor shall externalise all strings in ICU MessageFormat, support right-to-left scripts, per-user locale, time zone and number formats, translatable configuration names (statuses, fields, types), and a community translation workflow, shipping English plus at least German, French, Spanish, Portuguese (Brazil), Japanese and Chinese (Simplified) at release 1.0. | (1) A pseudo-locale build shows no hard-coded strings. (2) Status names translated per locale display in the user's language. | M1 | M | Jira (translations, dropped by Atlassian's migration tool) |
| NFR-007 | **Browser and device support.** Taskmoor shall support the latest two versions of Chrome, Edge, Firefox and Safari, mobile Safari and Chrome, and layouts from 360 px wide. | (1) The end-to-end suite passes on each supported browser. | M1 | M | Product decision |
| NFR-008 | **Security engineering and supply chain.** Taskmoor shall follow OWASP ASVS level 2, scan dependencies and containers on every build, sign releases and publish SBOMs, run an external penetration test before each major release, and publish security advisories with a disclosure policy. | (1) A build with a critical known vulnerability fails. (2) Each release has a signature and SBOM. | M1 | M | Compliance needs of self-hosters |
| NFR-009 | **Resource footprint.** Taskmoor's all-in-one install shall idle under 1.5 GB of RAM including PostgreSQL and keep the backend image under 500 MB compressed. | (1) Measured idle memory and image size are reported in CI and fail the build above the limits. | M1 | S | Report recommendation (Plane 4 GB floor, Sentry 16 GB) |
| NFR-010 | **Compatibility policy.** Taskmoor shall keep each native API major version for at least 24 months after deprecation, keep the Jira shim stable across minor releases, version the extension API semantically, and serve frontend kits one version back (API-018). | (1) The previous minor release's API contract tests pass on the current release. | M1 | M | Report recommendation |
| NFR-011 | **AI-optional operation.** Taskmoor shall work fully with no AI key: AI controls are hidden, nothing errors, and duplicate suggestions and similar-item lookups use the bundled local embedding model (AI-012). | (1) The full end-to-end suite passes with AI unconfigured. (2) No AI control is visible when no provider is set. | M1 | M | User requirement |
| NFR-012 | **AI isolation.** AI calls shall never sit on the critical path of non-AI actions: they run asynchronously or on explicit request, have timeouts, and a slow or failing provider does not change non-AI latency. | (1) With the provider responding after 60 s, item open and create still meet section 3 targets. | M1 | M | User requirement |
| NFR-013 | **Zero-configuration deployment targets.** The frontend kit uploaded to a plain static file server on a different origin from the backend shall pass the end-to-end suite with zero manual configuration, and a fresh VM shall reach a working app on a domain in under 15 minutes. | (1) A nightly CI job builds both kits, installs the backend kit on a fresh VM, uploads the frontend kit to a plain static server on another origin, and runs the end-to-end suite without manual steps. (2) The same job records total time from VM creation to first sign-in and fails above 15 minutes. | M1 | M | User requirement (Builder) |
